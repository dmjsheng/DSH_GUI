# DSH GUI V0.3 Implementation Plan

> **Execution note:** implement in `D:\DSH_GUI` after user approval. Keep the external Harness boundary at `D:\DSH`; do not modify Harness source.

## Goal

Make the Electron wrapper compatible with Harness `0.1.2-rc.1` authentication and provide a recoverable desktop shell: persisted configuration, startup diagnostics, safe LAN opt-in, single-instance behavior, and tray controls.

## Scope

- Update the backend controller to treat HTTP 401 as an online/auth-required Harness endpoint.
- Resolve the token URL from managed-process output or existing Harness startup logs, while redacting tokens in GUI-owned logs and diagnostics.
- Add a small JSON configuration store in Electron userData with D drive defaults and a `lanAccess` opt-in.
- Add main/preload IPC for status, retry, restart, diagnostics, and configuration changes.
- Add single-instance and tray behavior.
- Replace the static loading/error-only renderer with a compact startup/recovery surface; keep the official Harness Web UI as the main work surface.
- Add focused unit tests before each production change and run the existing test suite plus a portable build.

## Non-goals

- No rewrite of the Harness chat UI or RPC protocol.
- No automatic third-party plugin installation.
- No automatic deletion or force-killing of externally owned Harness processes.
- No bundled Node.js or Harness runtime in V0.3.

## Task 1: Lock the backend behavior with tests

1. Extend `test/backend.test.js` with failing cases for:
   - `probeHttp()` accepting 401 as an online endpoint.
   - extracting a matching token URL from Harness output.
   - redacting token query values from diagnostics/log lines.
   - resolving an existing authenticated endpoint without spawning another process.
   - reporting a useful error when an authenticated endpoint has no token URL.
   - using `0.0.0.0` as the bind host only when LAN access is enabled while keeping the local GUI URL on loopback.
2. Run `pnpm test` and confirm these new tests fail for the intended missing behavior.

## Task 2: Implement token-aware HarnessController

1. Add small pure helpers in `src/backend.js` or a nearby module for URL extraction, token redaction, endpoint classification, and bind-host resolution.
2. Make `probeHttp` distinguish online/auth-required from unavailable without exposing response bodies.
3. Make `createHarnessController.start()` return the authenticated URL and reuse an existing service when possible.
4. Capture child stdout for token resolution but write only redacted output to the GUI log.
5. Read the newest matching `startup-web-*.out.log`/`gui-web.out.log` when reusing a service started by the Windows task.
6. Add a controller status snapshot with ownership, PID, endpoint state, DSH version, and last error.
7. Run the focused tests, then the full GUI test suite.

## Task 3: Persist configuration and expose IPC

1. Add `src/config-store.js` with defaults, strict normalization, atomic-ish write-through, and `lanAccess: false` by default.
2. Add IPC handlers in `src/main.js` for `get-status`, `retry-start`, `restart`, `get-config`, `save-config`, `open-logs`, and `copy-diagnostics`.
3. Restrict preload exposure to these typed, narrow commands; keep Node APIs out of the renderer.
4. Make configuration updates validate paths/ports and require a restart for bind-host changes.
5. Add tests for defaults, normalization, malformed config recovery, and LAN opt-in persistence.

## Task 4: Add desktop lifecycle

1. Add Electron single-instance locking; a second launch focuses the existing window.
2. Add a tray icon/menu with show, restart backend, open logs, and quit.
3. Track whether the controller created the child process. Only owned children may be stopped by the GUI.
4. Add `before-quit` cleanup without terminating an externally owned Harness.
5. Add focused tests for ownership decisions where the behavior can be tested without Electron.

## Task 5: Replace the startup/recovery surface

1. Add renderer status rendering for checking, starting, authenticated, ready, and failure states.
2. Add actions for retry, restart, open logs, copy diagnostics, settings, and LAN toggle.
3. Show the local URL and LAN URLs without showing token values.
4. Show a direct explanation when the endpoint is online but authentication is missing or stale.
5. Keep the official Harness page loaded only after the controller returns a validated access URL.

## Task 6: Verify and package

1. Run `pnpm test` in `D:\DSH_GUI`.
2. Run the DSH CLI version/help checks and a token URL HTTP check against the upgraded `D:\DSH`.
3. Run `pnpm build`/`pnpm dist` as available and inspect the portable artifact.
4. Manually verify cold start, existing scheduled-task reuse, restart, computer-restart readiness, token authentication, port conflict, and LAN-off default.
5. Review `git diff` for token leakage and unrelated changes.

## Acceptance

- The GUI loads Harness `0.1.2-rc.1` through the token URL instead of treating 401 as a dead backend.
- A second GUI launch does not create a second Electron window or Harness process.
- An externally owned scheduled-task Harness is reused and is not killed when the GUI exits.
- LAN access is off by default and enabling it is visible, explicit, and restart-aware.
- Existing tests and new regression tests pass; the portable build completes.
